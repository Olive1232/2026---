## 已拍板的决定（2026-10-02）

| # | 决定 | 对架构的影响 |
|---|---|---|
| D1 | **是 roguelite**，不是 incremental | 钱包用单一 `int`；**不做**大数运算、挂机产出、离线收益、tick 经济 |
| D2 | **钱币品质只影响价值** | `CoinQuality` 纯粹是「外观 + 面额」；`Wallet` 只累加 int，不分类存储；`corpse_offered` 信号只传价值不传品质 |
| D3 | **一次只能扛 1 具尸体** | `is_carrying()` 返回 `bool`；不需要载重上限配置；不需要尸体堆叠 |
| D4 | **尸体存在时长可调** | 放进 `EnemyData.corpse_lifetime`（**按敌种配**，比全局常量灵活），默认 30 秒；敌人被替换时走 `corpse_expired` 强制回收 |

## 0. 一句话概括

第一人称战斗 roguelite。循环是：

```
杀生物 → 扛尸体 → 丢进洞 → 洞喷钱 → 捡钱 → 去商店 → 锻造插店长 → 换来神剑
   ↑                                                                      │
   └──────────────── 拿新剑回去清场（新剑可破特定障碍）←──────────────────┘
```

**注意**：策划案写的是"增量游戏"，但描述出来的循环其实是 **roguelite 循环**（一波波清场 + 装备升级），
不是数值指数增长的 incremental（那种通常有挂机产出、离线收益、指数级数值）。
这直接影响架构：**不要**按 incremental 去做大数运算和 tick 经济系统。
→ 见「待策划确认 Q1」。

## 1. 拆分原则

1. **先跑通循环，再堆内容。** 五个环节（战斗/搬运/献祭/商店/神剑）任意一环缺失，游戏都不成立，
   所以每环先做"能用的丑版本"，不做打磨。
2. **数据驱动。** 剑、钱币品质、涌现参数、敌人属性全部走 `.tres` 资源，
   让策划能自己调而不用改代码（策划是别人，这条尤其重要）。
3. **接口先行。** 先定好各系统之间的信号与函数契约（见第 4 节），
   让大家能并行开工不互相堵。
4. **不过度设计。** 单人开发 + 尚在验证玩法，不引入 ECS、不引入复杂状态机框架。
   每个系统一个 autoload 或一个基类就够。

### 明确不做（至少 MVP 阶段）

- ❌ incremental 式指数数值 / 挂机产出 / 离线收益
- ❌ 存档系统（等玩法定型再说）
- ❌ 多人 / 联机
- ❌ 程序化生成地图（房间是手工搭的）
- ❌ 复杂布娃娃（尸体用静态网格即可）

## 2. 技术风险：先验证这 4 件事

**这一步必须在正式动工前做**，因为其中任何一条不成立，架构都要改。

| # | 风险点 | 为什么危险 | 验证方式 | 判定标准 |
|---|---|---|---|---|
| R1 | 高速挥剑的命中检测 | 剑扫过一帧位移可能很大，`Area3D` 会**穿透漏判** | 在 60fps 下挥剑砍快速横移的敌人 100 次 | 漏判率 0 |
| R2 | 大量钱币的性能 | "涌现很多钱币"可能是几百上千个 | 生成 800 个钱币看帧率 | 稳定 ≥ 60fps |
| R3 | 扛尸体时的碰撞 | 尸体带碰撞体会把玩家卡住/顶飞 | 扛着尸体走过窄门、贴墙 | 不卡死、不抖动 |
| R4 | 洞的"掉进去"判定 | 要能区分"玩家走进洞"和"尸体被献祭" | 分别测试 | 各自触发正确 |

R1 的倾向方案：**用 `PhysicsDirectSpaceState3D.intersect_shape` 做扫掠检测**
（记录剑上一帧与当前帧的碰撞形状，做插值扫掠），而不是单纯靠 `Area3D` 的 `body_entered`。
R2 的倾向方案：**对象池 + 自己算速度**，不要每个钱币一个 `RigidBody3D`。

`SwordData` 建议字段：

```gdscript
class_name SwordData extends Resource
@export var display_name: String
@export var damage: float = 10.0
@export var range_m: float = 2.2          # 有效距离
@export var arc_degrees: float = 90.0     # 挥砍扇形角度
@export var windup: float = 0.12          # 前摇
@export var cooldown: float = 0.45        # 冷却
@export var swing_mesh: Mesh
@export var view_offset: Vector3          # 在第一人称里的位置
@export var damage_tags: PackedStringArray = []   # ["physical","fire",...]
@export var break_tags: PackedStringArray = []    # 可破除的障碍类型
@export var tint: Color = Color.WHITE     # 神剑的视觉区别
```

> `break_tags` 就是"某些强化后的剑可以破除某些障碍"的实现方式：
> 障碍带一个 `required_break_tag`，剑的 `break_tags` 含它才能破坏。**不要**写成一堆 `if 剑==火剑`。

## 4. 接口契约（先冻结，方便并行）

```gdscript
# ---- EventBus（autoload，全局广播，避免系统间硬引用）----
signal enemy_died(enemy: Node3D, corpse: Node3D)
signal corpse_grabbed(corpse: Node3D)
signal corpse_released(corpse: Node3D)
signal corpse_offered(corpse: Node3D, quality: int)
signal coins_erupted(count: int, quality: int)
signal coin_collected(value: int, quality: int)
signal wallet_changed(total: int)
signal forge_item_grabbed(item: Node3D)
signal forge_item_inserted(item: Node3D)      # 插进店长
signal shopkeeper_struck(by: Node3D)          # 左键砍到店长
signal sword_granted(sword: SwordData)
signal obstacle_broken(obstacle: Node3D)
signal room_cleared(room: Node3D)

# ---- HitInfo（伤害传递结构）----
class_name HitInfo extends RefCounted
var damage: float
var source: Node3D
var tags: PackedStringArray     # ["physical","fire",...]
var knockback: Vector3

# ---- 搬运算力（Player 暴露给搬运系统）----
func set_carry_weight(weight: float) -> void
func is_carrying() -> bool
```

**契约纪律**：谁要用别的系统，只准走 `EventBus` 或调用上面这几个公开方法，
不准 `get_node("../../某个具体路径")`。这条能省掉后期大量返工。

## 5. 里程碑

### MVP（建议目标：跑通完整循环，画面全用占位）

**完成标准：** 打开游戏 → 在主房间 → 走去战斗房 → 砍死 2 只怪 → 扛一只尸体回来 →
丢进洞 → 喷出钱币并自动飞向玩家 → 去商店 → 长按右键拿货 → 走到店长前松手 →
左键砍店长 → 拿到一把和初始剑手感不同的剑。

| 里程碑 | 内容 | 依赖 |
|---|---|---|
| **MS0** | 风险验证 R1–R4（可写一次性测试脚本，验完即弃） | 无 |
| **MS1** | M0 + M1 完成 | MS0 |
| **MS2** | M2 + M3 完成 → **能砍死怪** | MS1 |

### 关键设计取舍（为什么这么做）

1. **`corpse_offered` 不带品质参数。** 因为 D2 定了品质只影响价值，

2. **`corpse_lifetime` 放在 `EnemyData` 而不是全局常量。** 不同生物可以有不同腐烂时间，

3. **`enemy_died` 与 `corpse_spawned` 分成两个信号。** 死亡瞬间尸体还没生成，

4. **数据类脚本放 `Resources/Scripts/` 而非 `Scripts/`。** 让策划改数值时不用翻到代码目录。
5. **`break_tags` / `damage_tags` 用字符串标签，不用枚举或布尔量。**
   这样"火剑能烧藤蔓"是数据配置，加新剑新障碍零代码改动。

### 关键决策变更：命中检测用 Area3D，不用扫掠

第 2 节的 R1 原本倾向"用 `intersect_shape` 做扫掠检测"，**现已按需求决定改用 `Area3D`**。

为缓解 `Area3D` 的固有弱点（高速挥砍时一帧位移过大可能漏判），做了三处加固：

1. **伤害盒比剑身更厚更大**：1.4 × 1.0 × (range×0.78)，比视觉剑身宽得多
2. **不依赖 `body_entered` 信号**：信号只在"进入那一帧"触发，容易整段判定错过。
   改为判定期内**每个物理帧主动轮询** `get_overlapping_bodies()`
3. **单次挥砍命中登记表** `_hit_this_swing`：既防止一刀多次伤害，也是"这一刀砍中了什么"的依据

**已知残留风险**：极高速挥砍 + 极薄目标仍有理论漏判可能。
若日后实测发现漏判，回退方案是把 `_poll_hits()` 换成 `PhysicsDirectSpaceState3D.intersect_shape` 扫掠——
**接口不变**（都是"判定期内找出区域内的可伤害目标"），替换成本低。

### 怎么自己调剑的位置和角度（策划/程序都看这里）

**改这一个文件：** `Resources/Swords/sword_starter.tres`

#### 位置：`view_offset`

```
view_offset = Vector3(-0.27, 0.0, 0.0)
                   ↑x      ↑y    ↑z
```

| 轴 | 负值方向 | 正值方向 | 直觉 |
|---|---|---|---|
| **x** | 往左（画面内侧） | 往右 | 想往中间挪就调小 x |
| **y** | 往下 | 往上 | 想让剑沉下去就调小 y |
| **z** | 往前（离相机更远，看起来更小） | 往后（靠近脸，看起来更大） | 主要影响剑的"大小感" |

#### 角度：三个静止姿态参数

| 参数 | 含义 | 怎么调 |
|---|---|---|
| **`rest_yaw`** | 水平朝向（剑尖左右摆） | 0 = 正对前方；**负值 = 剑尖偏右**；正值 = 偏左 |
| **`rest_pitch`** | 俯仰（剑尖上下抬） | **负值 = 剑尖朝下压**；正值 = 朝上抬 |
| **`rest_roll`** | 自转（刃朝哪边） | 0 = 刃朝上下（竖直刀身）；**90 = 刃朝左右（平躺刀身）** |

> `swing_pitch` 是**挥砍时额外压下的角度**，在 `rest_pitch` 基础上叠加，
> 不控制待机姿态。想调"剑一开始的朝向"要用 `rest_pitch` / `rest_roll` / `rest_yaw`。

**推荐操作流程（实时预览）：**

1. 在 Godot 里**运行测试场地**（F5）
2. 在 FileSystem 面板点开 `Resources/Swords/sword_starter.tres`
3. 在右侧检视器里直接改数值
4. **游戏窗口里的剑会立刻跟着动** —— 位置和三个角度都实时生效，不用重载场景

> 实时生效靠 `SwordData.view_changed` 信号：`view_offset` / `rest_yaw` / `rest_pitch` /
> `rest_roll` 四个字段的 setter 都会发这个信号，`Sword.gd` 收到后立刻重算位置与姿态。

**⚠️ 三个必须知道的点：**

- **改的是资源文件，会影响所有用它的剑。** 现在只有 Player 用 `sword_starter`，
  所以没有副作用；将来若多个角色共用同一把剑的数据，改位置会一起变。
  要给某一把单独调，就给它复制一份 `.tres`。
- **改完记得保存**（Ctrl+S），否则关掉编辑器就丢了。
- **不要改场景里 `Mount` 节点的 `position` / `rotation`。**
  代码在 `_ready()` 和每帧的 `_process()` 里都会覆盖它们。

### 第二轮修的两个旋转 bug（重要，别再踩）

1. **yaw 被叠加了两次。** `WeaponPivot` 节点上残留着第一版写死的 `-35°`，
   而代码每帧又往里写 `rest_yaw=-10°`，**合计 -45°**，剑歪得离谱。
   → 已把 `WeaponPivot` 的旋转清零，朝向左后完全由脚本控制。
2. **静止姿态的 pitch 被硬编码成 0。** `_drive_animation()` 里写的是
   `_apply_pose(rest_yaw, 0.0)`——第二个参数直接给 0，
   所以 `swing_pitch` 只在挥砍那一瞬生效，**待机时怎么调都没反应**。
   → 新增独立的 `rest_pitch`，`swing_pitch` 回归"挥砍时额外压下"的本义。

### 第三轮修正：剑的初始姿态 + 判定与表现解耦

**需求**：剑柄在画面右下角，剑尖指向右上角。

#### 定稿参数（`sword_starter.tres`）

| 字段 | 值 | 说明 |
|---|---|---|
| `view_offset` | `(0.22, -0.32, -0.42)` | 挂点位置 |
| `rest_yaw` | `-40` | 水平朝向，负值 = 剑尖偏右 |
| `rest_pitch` | `70` | 俯仰，**正值 = 朝上抬** |

实测屏幕坐标：**剑柄 (879, 435) 右下**，**剑尖 (1089, 52) 右上**，均在屏内。

#### 符号约定修正（之前文档写反了，实测确认）

| 字段 | 正确约定 |
|---|---|
| `rest_yaw` | **负值 = 剑尖偏右**；正值 = 偏左 |
| `rest_pitch` | **正值 = 剑尖朝上抬**；负值 = 朝下压 |
| `view_offset.y` | **越负 = 画面越靠下**（与直觉相反） |

#### `rest_pitch` 的"摊薄"效应

抬高角**不等于** `rest_pitch`。yaw 不为 0 时俯仰会被摊薄：

```
实际抬高的正弦 = sin(rest_pitch) × cos(rest_yaw)
```

例：`rest_yaw=-28`、`rest_pitch=46` → 实际抬高约 39°。
另外剑尖离相机只有约 1 米，**屏幕最多只能显示到垂直 ±27°、四角约 50°**，
所以"剑尖朝左上 60°"这类需求在视觉上做不到——超视锥了。

#### 重大修复：判定范围与剑的姿态解耦

**问题**：伤害区域原本挂在剑的表现层级下，剑一抬高，判定区就跟着转去扫天空。
实测 `rest_pitch` 超过 30° 后**伤害直接归零**（40°/50°/60°/70° 全是 0）。

**修法**：把伤害区域从表现层级里提出来，挂到只继承水平横扫的锚点上：

```
WeaponPivot                  ← 水平横扫 yaw（脚本写）
├── HitAnchor                ← 只继承 yaw，不继承剑的俯仰/自转/偏移
│   └── HitRig               ← 固定下倾 14°（HITBOX_LEVEL_PITCH 常量）
│       └── Hitbox (Area3D)
│           └── Shape
└── Mount                    ← 脚本控制：位置 + 俯仰 + 自转
    └── Pivot                ← 水平横扫 yaw（脚本写）
        ├── Mesh
        └── Guard
```

**验证结果**：`rest_pitch` 取 0/30/50/70/90 度，伤害**全部为 10.0**。
剑的姿态从此纯属表现，改姿势不会影响能不能打中。

> 这个坑如果不修，后面每加一把"造型不同"的剑都会莫名其妙打不中人——
> 而且极难排查，因为表现看起来完全正常。

#### 测量工具的注意事项（避免误判）

调试期间剑的姿态用 `Camera3D.unproject_position()` 量屏幕坐标。
**游戏窗口失焦时主循环会暂停**，此时：

- `unproject_position()` 可能返回 `(0,0)` 或天文数字（如 `8.8e9`）
- `await get_tree().physics_frame` / `create_timer` **永远不会返回**，eval 直接超时
- `physics_interpolation_mode` 相关节点读到的 transform 可能是**上一帧的旧值**

对策：`RenderingServer.force_sync()` 强制刷新；关键测量在**同一次 eval 内**完成；
引擎报 `EVAL_GAME_NOT_READY` 时重新 `project_run` 让窗口回到前台再试。

### 第四轮修正：移动时画面抖动

**现象**：移动时看靶子会**微微震动**。

**根因（实测确认）**：

| 设置 | 值 |
|---|---|
| 显示器刷新率 | **200 Hz** |
| `physics/common/physics_ticks_per_second` | **60** |
| `physics/common/physics_interpolation` | **false**（引擎默认） |
| V-Sync | 开启 |

相机的位置每 **16.7ms** 才更新一次，画面却每 **5ms** 重绘一次。
不做插值时，渲染读到的相机变换是"阶梯状"的——相机在渲染帧里停住不动，
于是相对场景（靶子）就**反向往回跳**。这就是抖动来源。

**这是第二轮修正的副作用**：第二轮删掉 `physics_interpolation_mode = 1`
修好了"视角旋转与位移不同步"，但把位移的平滑也一并删掉了。

**修法（两步必须都做）**：

1. `project.godot` 启用 `physics/common/physics_interpolation=true`
   → 位移在物理帧之间被平滑到渲染帧
2. `player.gd` 把鼠标视角从 `_unhandled_input` **移到 `_process`**
   → 输入只累积到 `_look_delta`，渲染帧统一应用。
   若旋转仍留在输入回调里，就会重演第二轮那个"旋转走渲染帧、位移走物理帧"的不同步

**验证**：命中未受影响（两刀各 10 伤害，状态机正常）。

> **无法用脚本证实的部分**：插值后的变换从 GDScript 读不到——
> 实测 `Camera3D.global_position` 与 `Player.global_position` 每帧完全相等（差 0.0000），
> 因为它返回的是物理变换而非渲染变换。所以"抖动是否消失"只能靠肉眼确认。

### 关于移动手感的剩余问题

`player.gd` 目前仍是**瞬时赋值速度**，没有加减速：

```gdscript
if direction:
    velocity.x = direction.x * speed      # 瞬间满速
else:
    velocity.x = move_toward(velocity.x, 0, speed)   # 减速率用了 speed 本身
```

表现为"起步硬、刹车黏（像在冰上）"。已定位但**尚未修**，
需要新增 `ground_accel` / `ground_friction` 两个参数。
这与上面的抖动是两个独立问题。
